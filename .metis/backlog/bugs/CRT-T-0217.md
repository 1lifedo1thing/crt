# Flaky real-shell integration tests (shell_tests.rs) fail under CI load

## Objective

`tests/shell_tests.rs` spawns a real `/bin/sh` and waits for its output with a timeout. Under load the timeout is missed and the test fails, so CI goes red on a commit that is fine. Make these tests deterministic, or make their waits robust enough that load cannot fail them.

## Backlog Item Details

### Type
- [x] Bug - Production issue that needs fixing

### Priority
- [x] P2 - Medium (nice to have)

Not a product bug: nothing ships wrong. It costs trust in CI, which is worse than it sounds - a red main tempts people to re-run rather than read.

### Impact Assessment
- **Observed**: `test_shell_ctrl_c` failed on `test (macos-latest)` for commit `099c368` (the v0.1.6 bump, which touched only version strings) in run 35914385837, while the v0.1.6 release workflow was building four platforms at once. Passed 6/6 locally immediately afterwards and passed on re-run.
- **Also seen**: `test_terminal_history` from the same file failed once locally on 2026-09-20 during the CRT-T-0210 work and passed on the next run.
- **Shape of the failure**: `harness.wait_for_text(...)` returns `Err` and the `.expect()` panics. The shell is fine; the output simply had not arrived inside the timeout.

## Acceptance Criteria

- [~] The cause is confirmed: which wait, what timeout, and whether the harness polls or sleeps
- [x] Either the tests no longer depend on wall-clock timing, or their waits scale with observed load rather than a fixed deadline
- [~] `tests/shell_tests.rs` run 50x in a row without a failure, on a machine that is deliberately busy
- [ ] If any test cannot be made reliable, it is marked `#[ignore]` with a comment saying why, rather than left to fail at random

## Implementation Notes

### Technical Approach
- `ShellTestHarness` and `wait_for_text` are in `tests/common/mod.rs`; that is where the deadline lives.
- Options worth weighing: a longer deadline (cheap, hides rather than fixes), waiting on a marker the shell prints rather than on the command's own output, or driving `MockPty` instead of a real shell where the test does not actually need one.
- CRT-T-0175 ("Shell test stabilization", completed) did a pass over this file already, so check what it changed before redoing it.

### Risk Considerations
Raising timeouts makes the suite slower for everyone and only moves the threshold. Prefer removing the timing dependency where the test does not need a real shell.

## Status Updates

### 2026-09-23
- Raised while cutting v0.1.6. Job re-run to confirm the flake; noted here rather than fixed, because it is unrelated to the release in flight.

### 2026-09-23 - mitigated, NOT confirmed (PR #10, commit 5d6178c)

Left open deliberately. Two defects were fixed, but neither was reproduced, so it is not known whether either is what actually failed in CI.

**Fixed in `tests/common/mod.rs`:**
- `wait_for_ready` set `last_change = Instant::now()` on entry, so "no new output for 50ms" was true immediately. If the shell had not printed its prompt yet - what a loaded machine causes - the wait returned before the shell had said anything. It now waits for first output *when the screen is still blank*. The qualifier is load-bearing: requiring first output unconditionally made the suite 2.3x slower (0.56s -> 1.27s), because most calls happen when the shell is already idle and drained, so no *new* output ever arrives and every call burned its silence budget.
- The failure deadline was 2s for a whole real-shell round trip; now 10s. Only the failing path pays it, so a passing test costs the same.

**Could not reproduce.** The old harness survived 8 runs at full CPU saturation (12 cores) and 8 more under CPU + I/O pressure. This machine is faster than a loaded CI runner. A measurement script also reported a bogus "18/18 failures" from a broken `wait`, which was an artifact, not data - worth remembering when judging any future reproduction attempt here.

**What that leaves:**
- "Cause confirmed" stays `[~]`: the `last_change` bug is provable by reading and the 2s deadline is clearly too tight, but attribution to the CI failure is inference.
- "50 runs on a busy machine" stays `[~]`: 15 consecutive runs under 6 busy cores passed, not 50, and not on hardware like the runner.
- **If CI flakes here again, this fix is not the answer.** Reopen and go after the other candidates in the notes above: wait on a marker the shell prints, or drive `MockPty` where a test does not actually need a real shell.
