# Background update check with toast, menu entry and [updates] config

## Parent Initiative

[[CRT-I-0034]] In-place self-update with update notifications. Phase 3: ships the notification on its own, for every install kind.

## Objective

CRT tells the user, inside the emulator, when a newer release exists (REQ-001, REQ-002, REQ-007, REQ-008), without blocking the UI (NFR-001) and without any network access when checks are disabled (NFR-006, NFR-007). Managed and dev installs get the right upgrade hint.

## Acceptance Criteria

## Acceptance Criteria

- [x] `crt-update::fetch::Fetch` trait (`fn get(&self, url, dest: Dest) -> Result<(), FetchError>` with `Dest::{Memory, File(path)}`) and a `CurlFetch` impl that runs `curl -fsSL --connect-timeout 5 --max-time <n> -A crt/<ver>` as a subprocess; missing `curl` is a distinct error with a message naming it. `MemoryFetch` in tests.
- [x] `[updates]` in `config.rs`: `check: bool = true`, `interval_hours: u32 = 24`; documented in `assets/config.toml`.
- [x] `~/.config/crt/state/update.toml` (`UpdateState { last_check, last_notified_version, last_finished_version }`), created on demand; unreadable/corrupt state is treated as empty with a warn log.
- [x] After the first presented frame the app spawns one worker thread that fetches `SHA256SUMS` (only when `check` is on and `now - last_check >= interval`), parses it, classifies the install, and sends `UpdateEvent::{Available { version, kind }, UpToDate, Failed(err)}` over a channel, then wakes the loop with a new `WakeReason::Update`.
- [x] On `Available`: info toast "CRT vX.Y.Z is available — Update from the menu" (self-replaceable kinds) or "… — installed via <manager>, run `<hint>`" (managed) or "… — rebuild from source" (dev), shown at most once per version per interval (`last_notified_version`); the update menu entry is retitled "Update to vX.Y.Z…" and stays until applied or the version changes.
- [x] Menu: macOS native menu gets "Check for Updates…" under the app menu; Linux/Windows context menu gets the same item. "Check for Updates…" runs the check immediately regardless of `interval_hours` and shows "You're up to date (vX.Y.Z)" or the failure toast. With `check = false` the menu item still works (the user asked); the launch check never runs.
- [x] Self-replaceable kinds: the retitled entry does nothing yet beyond a toast "In-place update coming in a later release; re-run the install script" until CRT-T-0214/0215 land (keep the wiring point obvious). Managed/dev kinds: the entry opens the release page with `open`.
- [x] `crt --version` prints `crt 0.1.6 (<install kind>)`; exits before any window is created.
- [x] Failure toasts per REQ-010 for offline / non-200 / parse error, each with a distinct message and a `warn` log; a failed check still updates `last_check` so an offline machine does not retry every launch.
- [x] Tests: worker logic factored as `fn run_check(fetch: &dyn Fetch, state: &mut UpdateState, now, cfg, kind) -> Option<UpdateEvent>` and unit-tested with `MemoryFetch` for: newer / same / older version, interval not elapsed, `check = false`, fetch error, parse error, notified-once-per-version. Toast wording lives in one `fn` with a test per install kind.
- [x] Manually verified on macOS: launch with a fake older `CARGO_PKG_VERSION` (env override for dev builds, `CRT_FAKE_VERSION`, debug builds only) and see the toast; `check = false` produces no `curl` process (check with `RUST_LOG=debug`).

## Implementation Notes

### Technical Approach
- Reuse the existing `Waker` (`src/app/mod.rs`) and add `WakeReason::Update`; drain the channel in `about_to_wait` next to the PTY drain.
- The worker owns its `CurlFetch`; the main thread never blocks on it. Kill the child on app exit via `Child::kill` in the worker's drop path if still running.
- `CRT_FAKE_VERSION` is compiled only under `debug_assertions`.

### Dependencies
CRT-T-0211 (the file exists on releases), CRT-T-0212 (manifest + classification).

### Risk Considerations
Nagging: the once-per-version-per-interval rule and the persistent-but-quiet menu entry are the whole anti-nag design; get the state transitions unit-tested rather than eyeballed.

### 2026-09-23 - done (commit a3ab352)

Workspace: 832 tests pass (was 777), clippy clean, `cargo fmt` applied.

**Live smoke test on macOS**, two runs against a temp `CRT_CONFIG_DIR` with `CRT_FAKE_VERSION=0.0.1` and `RUST_LOG=crt=debug,crt_update=debug`, each killed after 9s:

- `check = true`: `install kind: development build (Dev)` -> worker ran -> real `curl` request -> **404**, because v0.1.5 predates CRT-T-0211 and has no `SHA256SUMS` yet. Mapped to `FetchError::Http`, logged at warn, no toast (background failure). `state/update.toml` written with `last_check`, so the next launch backs off. That is REQ-001, REQ-010 and the back-off rule confirmed against the real network.
- `check = false`: `update checks are disabled; no network access`, and **no state file at all** - nothing was fetched and nothing was written. NFR-006/NFR-007 confirmed.
- `crt --version` / `-V` print `crt 0.1.5 (development build)` and exit before any window.

**Still unverified live:** the "available" toast and the retitled menu entry, because no published release carries `SHA256SUMS` yet. The decision logic is covered by unit tests (`run_check` x11, `Updates::apply` x6) and the plumbing around it is confirmed by the run above; the remaining gap is the same one CRT-T-0211 leaves, and both close on the next release.

**Deviations from the sketch above, deliberate:**

- `Fetch` has two methods (`get_text` for the small document, `download` for the tarball) instead of one `get` with a `Dest` enum. The two transfers want different error handling and `download` needs the `.part`-then-rename behaviour; one method taking a destination enum obscured both.
- `run_check` takes `CheckConfig` (enabled, interval, user_requested, running_version) and does not take the `InstallKind`. The kind only affects wording, so it stays with the app and `availability_message(version, kind)` formats with it. That keeps `run_check` free of anything platform-shaped.
- `UpdateEvent` has a fourth variant, `Unreadable { reason }`, split out from `Failed`. A release we cannot parse is not a network problem and deserves different wording; it also must not be reported as "up to date".
- Background failures are silent (logged only); only a user-requested check toasts a failure. A laptop that wakes on a train should not be nagged about it.
- The context menu entry is added on every platform, not just Linux. It is the only menu on Linux, and on macOS it mirrors the app-menu entry rather than being a second way to do something different.
- Toasts land on the focused window, falling back to any window, falling back to the log if none exists yet.

**Notes for CRT-T-0214:**
