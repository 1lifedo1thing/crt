# In-place apply for the Linux user binary and the crt update CLI

## Parent Initiative

[[CRT-I-0034]] In-place self-update with update notifications. Phase 4: the first self-replacing path, on the simpler layout (a single file), plus the headless CLI that scripts and the macOS task reuse.

## Objective

A `UserBinary` install (default `~/.local/bin/crt`) can replace itself from the menu or from `crt update`: download, verify, unpack, atomic swap, previous version kept as `crt.old`, every failure leaving the install untouched (REQ-004, REQ-005, REQ-009, REQ-010, REQ-012, NFR-003, NFR-004).

## Acceptance Criteria

## Acceptance Criteria

- [x] `crt-update::apply` module: `fn apply(plan: &UpdatePlan, fetch: &dyn Fetch, progress: &mut dyn FnMut(Stage)) -> Result<Applied, ApplyError>` where `UpdatePlan { kind: InstallKind, asset: Asset, staging_dir }` and `Stage::{Downloading, Verifying, Unpacking, Installing}`.
- [x] Locking: `<staging>/lock` created with `create_new`, holding the pid; a live pid → `ApplyError::InProgress`; a dead pid → stale lock removed. Released on every exit path (RAII guard).
- [x] Staging dir is `<install_dir>/.crt-update/`, created fresh; leftover staging dirs from a crashed run are removed at the start of the next apply and at app launch.
- [x] Download to `<staging>/<asset name>` via `Fetch::get(.., Dest::File)`; sha256 (`sha2`) compared to the manifest before anything is unpacked; mismatch → `ApplyError::ChecksumMismatch { expected, actual }` and the file deleted.
- [x] Unpack with `tar` + `flate2` into `<staging>/unpacked/`, rejecting entries with `..` or absolute paths; the Linux layout yields `crt` and `icons/`.
- [x] Swap: `rename(current, current.with_extension("old"))` then `rename(staged_binary, current)`; on failure of the second rename, rename `.old` back and report `ApplyError::Swap`. Executable bit preserved. Staging dir removed afterwards.
- [x] `Applied { version, previous: PathBuf }` reported; the app shows "vX.Y.Z installed. It takes effect the next time you open CRT." and resets the menu entry. No restart prompt.
- [x] The menu entry from CRT-T-0213 now drives this for `UserBinary`; progress stages are shown as successive info toasts (rate-limited to one per stage).
- [x] CLI: `crt update` prints the same stages to stdout, exits 0 on success / 2 when up to date / 1 on failure; `crt update --check` reports only. Uses the same lock. Works without a display.
- [x] Every `ApplyError` variant maps to a specific toast/CLI message per REQ-010; permission denied names the path and points to the install script.
- [x] Integration tests (crate-level, both CI platforms): a temp dir with a fake `crt` binary (a shell script that prints its version), a `MemoryFetch` serving a tarball built in the test and a matching `SHA256SUMS`; assert: success swaps and keeps `.old`; checksum mismatch leaves everything untouched; lock held by a live pid refuses; stale lock proceeds; a read-only install dir fails with `PermissionDenied` and no `.old`; a tarball with `../evil` is rejected; the "current" binary keeps running during the swap (spawn it sleeping, swap, confirm exit code).
- [~] Manually verified on Linux (CI runner or VM): `install.sh` v0.1.5 install → `crt update` to a test release → new `--version`.

## Implementation Notes

### Technical Approach
- Progress: `curl` has no machine-readable progress on stdout; report stage transitions only (the tarballs are ~17 MB, a few seconds). Percentages are a later nicety.
- `Fetch::get` to a file must write to `<name>.part` and rename on completion so a partial download is never mistaken for a full one.
- Keep `apply` free of app types; the app maps `Stage`/`ApplyError` to toasts in one place.

### Dependencies
CRT-T-0213 (menu entry, state, `Fetch`). CRT-T-0215 reuses everything here except the layout-specific unpack/swap.

### Risk Considerations
The two-rename swap is only atomic on one filesystem; the staging dir being a sibling of the target guarantees that. Test the cross-device case (staging on tmpfs) fails cleanly rather than half-copying.

## Status Updates

### 2026-09-23 - done (commit 019110e, plus bundle fixes in CRT-T-0215)

`crates/crt-update/src/apply.rs`. 69 crate tests, 848 workspace tests, clippy clean.

**End-to-end verification against a real release, not just unit tests.** Debug builds (and release builds compiled with the `crt-update/dev-update-url` feature) honour `CRT_UPDATE_URL`, so a local directory can stand in for a GitHub release: `curl` takes `file://` URLs, so the real `CurlFetch` path, the real tarball, the real checksum and the real swap all run. A shipped build ignores the variable - an env var that redirects a program which *installs things* would be a way to feed it someone else's bytes.

Confirmed with an optimised binary installing over itself in a temp dir:
- classification says `user install` (a release build outside `target/`),
- `crt update --check` reports the local v9.9.9 and exits 0,
- a tampered tarball is refused and the installed binary is byte-identical afterwards.

**Design notes beyond the sketch:**

- `apply()` takes `UpdatePlan { kind, asset, version }` and a `&mut dyn FnMut(Stage)`; the layout (single binary / app bundle) is derived from the `InstallKind` rather than passed in, so the caller cannot pair a bundle with the wrong layout.
- Archive safety is a **two-pass** unpack: the first pass reads every entry path and writes nothing, so an archive containing `..` is refused outright rather than partially applied. Relying on `tar`'s own protection would still have created the safe entries first.
- The lock holds a pid, and a lock whose process is gone is taken over. A killed update would otherwise block every future one, and there is no daemon to clean up after it.
- `plan_update()` re-reads the release at apply time instead of caching the asset from the check. It is a few hundred bytes, and it means the download is verified against what the release says *now*, not what it said hours ago.
- `Stage::message` takes `Option<&Version>`, because the caller genuinely does not know the version until the release has been read.
- `ApplyError::ReleaseUnreadable` was added when the CLI needed it: "the release makes no sense" is not a network failure and should not be worded as one.

**Not done:** the Linux manual check. The code path is identical to the macOS single-binary path verified above (same `Layout::SingleBinary`), and the crate tests run on both CI platforms, but no real `install.sh` install on Linux was exercised. Worth doing on a Linux box or CI runner before this ships.
