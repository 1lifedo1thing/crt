# In-place apply for the macOS app bundle

## Parent Initiative

[[CRT-I-0034]] In-place self-update with update notifications. Phase 5: the same apply flow on the bundle layout, which is the common install.

## Objective

An `AppBundle` install (`/Applications/crt.app`) can replace itself from the menu or `crt update`: the whole bundle is staged, verified, de-quarantined and swapped by directory rename, with the previous bundle kept as `crt.app.old` (REQ-004, REQ-005, REQ-010, REQ-012, NFR-003, NFR-004).

## Acceptance Criteria

- [ ] `apply` handles `InstallKind::AppBundle`: staging dir is `<parent of bundle>/.crt-update/` (so `/Applications/.crt-update/`, hidden in Finder); the macOS tarball unpacks to `<staging>/unpacked/crt.app`; validation that `Contents/MacOS/crt` and `Contents/Info.plist` exist before any swap.
- [ ] Quarantine: `xattr -dr com.apple.quarantine <staged bundle>` run as the user, never sudo; failure is logged at debug and ignored (the attribute is not expected to be present; see initiative Context).
- [ ] Swap by two directory renames: `crt.app` → `crt.app.old`, staged `crt.app` → `crt.app`; second-rename failure restores the old bundle. If `crt.app.old` already exists from an earlier run it is removed first.
- [ ] Permission failure in `/Applications` (non-admin user) surfaces as `ApplyError::PermissionDenied { path }` with the toast "Could not replace /Applications/crt.app (permission denied). Re-run the install script to update." and nothing changed.
- [ ] The running process keeps working after the swap (it holds the old inode); verified by keeping a shell busy in a tab through the update.
- [ ] `open -n /Applications/crt.app` after the swap launches the new version cold (Gatekeeper does not block it: no quarantine attribute); LaunchServices shows the new version in About.
- [ ] Integration tests (both CI platforms, no real bundle needed): a fake `.app` tree with `Contents/MacOS/crt` (script) + `Info.plist`, tarball built in the test; assert success/`.old`/rollback-on-second-rename-failure/permission-denied (read-only parent)/missing `Info.plist` rejected/existing `.old` replaced.
- [ ] Manual verification on macOS with the real unsigned v0.1.5 bundle updated to a test release built by `release.sh`: swap succeeds as an admin user, the new bundle launches from Finder and from `open`, the About box shows the new version, and a non-admin account gets the permission-denied toast.
- [ ] `docs/how-to/update.md` gets the manual rollback line: `mv /Applications/crt.app.old /Applications/crt.app`.

## Implementation Notes

### Technical Approach
- Reuse CRT-T-0214's download/verify/unpack/lock; only `layout::{validate, swap}` differ per kind. Model as `enum Layout { SingleBinary, AppBundle }` chosen from `InstallKind`.
- Do not touch `Info.plist` or re-sign; when the codesigning initiative lands, a signed bundle survives directory rename unchanged, so this task needs no rework then.
- App Translocation only applies to quarantined bundles; with no attribute it does not trigger. If a user did somehow get a quarantined bundle (e.g. downloaded the tarball with Safari and installed by hand), the strip above handles the staged copy.

### Dependencies
CRT-T-0214.

### Risk Considerations
`/Applications` ownership is the main real-world failure; the message must make the fix obvious. Keep an eye on `crt.app.old` leaking if first-launch finish (CRT-T-0216) never runs; CRT-T-0216 owns the cleanup, and this task must not delete `.old` itself.
