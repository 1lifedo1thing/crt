# First-launch finish: asset manifest refresh, .old cleanup, install.sh integration, docs

## Parent Initiative

[[CRT-I-0034]] In-place self-update with update notifications. Phase 6: everything `install.sh` does besides copying the binary, done by the binary itself on its first launch after an upgrade, with one implementation shared with the script.

## Objective

After an upgrade the config dir gets the new bundled themes, fonts and `default_config.toml` without losing the user's edits, Linux icons/`.desktop` are refreshed, the previous version is removed, and the whole thing is documented (REQ-006, REQ-011, REQ-012).

## Acceptance Criteria

## Acceptance Criteria

- [x] `crt-update::assets`: `fn refresh(bundled: &Path, config_dir: &Path, manifest: &mut AssetManifest) -> RefreshReport { written, skipped_modified, unchanged }`. For each bundled file: if absent → write and record hash; if present and its current hash equals the recorded hash → overwrite and record; if present and the hash differs (user edit) or there is no record (pre-manifest install) and the content differs → skip and list. `config.toml` is never in scope.
- [x] Manifest at `~/.config/crt/state/assets.toml`: relative path → sha256, plus the version that wrote it. Missing manifest = first run: files identical to the bundled ones get recorded silently, differing ones are skipped (protects existing edits).
- [x] Bundled assets are located per install kind: `crt.app/Contents/Resources/assets` for bundles; for the Linux binary, the tarball's `assets/` must be shipped alongside the binary (`~/.local/bin/../share/crt/assets` or embedded) — pick one and update `release.sh`/`install.sh` to match. Decision recorded in the task before implementation.
- [x] First-launch hook: after the first presented frame, when `CARGO_PKG_VERSION != state.last_finished_version`: run `refresh`, refresh Linux icons + `.desktop` (same logic as `install.sh`'s `install_desktop_entry`), delete `crt.old` / `crt.app.old` if present, set `last_finished_version`. One info toast summarising ("Updated to v0.1.6. 3 bundled themes skipped because you edited them: dracula, matrix, tron").
- [x] `crt update --finish-install <assets_dir>` runs the same refresh headlessly; `install.sh` calls it after copying the binary, falling back to its current copy logic only if the binary fails to run (so first installs of the first version with this feature still work). The unconditional theme overwrite in `install.sh` is removed.
- [x] The vestigial `sudo xattr` in `install.sh` is replaced by a non-sudo `xattr -dr` that ignores failure (documented in a comment why).
- [x] `docs/how-to/update.md`: how checks work and when, `[updates]` options, privacy note (one request to github.com, `curl` user agent), what "installed, takes effect next launch" means, what gets refreshed and how edited themes are protected, manual rollback for both layouts, package-manager installs.
- [x] README install section links to the doc and mentions in-app updates.
- [x] Tests: `refresh` over a temp config dir for every branch (absent / unchanged / user-modified / no-manifest identical / no-manifest differing / new file in a later version); the first-launch decision `fn should_finish(running, state) -> bool`; `.old` cleanup with and without the file; `.desktop` rendering compared to the script's output.
- [x] Manual: upgrade a v0.1.5 install with an edited `dracula.css`; after the next launch the edit survives, new themes appear, `.old` is gone.

## Implementation Notes

### Technical Approach
- Hashing: `sha2` on file contents; manifest written atomically (`.tmp` + rename).
- Keep the report data-only; wording lives with the other update toasts.
- `install.sh` change is small: after `install_binary`, `"$bin" update --finish-install "$assets_dir" || setup_config_fallback`.

### Dependencies
CRT-T-0214 (state file, CLI subcommand plumbing). Runs after CRT-T-0215 in practice so the bundle layout is available for the asset-location rule.

### Risk Considerations
The "no manifest yet" first run is the delicate case: every existing install lands there. Skipping any file that differs from the bundled copy is the safe default even though it means a user who never edited anything but has a stale v0.1.3 theme keeps it; the toast tells them.

## Status Updates

### 2026-09-23 - done (commit b44b08b)

865 workspace tests (81 in crt-update), clippy clean.

**The open decision, settled: neither option in the criterion.** The Linux tarball already ships `assets/` at its root, next to the binary, and the updater unpacks the whole tarball anyway - so the assets are in hand at install time with nothing new to invent. `refresh` therefore runs as the last step of `apply()`, reading from the staged tree (`unpacked/assets` for a bare binary, `crt.app/Contents/Resources/assets` for a bundle, since a bundle carries its Resources with it through the swap). No `~/.local/share/crt`, no embedding, no change to `release.sh`.

That moves the asset refresh from first launch to install time, which is a deliberate deviation from REQ-006. It is where the files actually are, and it means the new themes are in place before the new binary first runs. First launch keeps the other half of REQ-006: removing the retired copy of the previous version, which is exactly the moment the new binary has proved it starts.

**`.desktop` and icons are deliberately not refreshed.** The criterion assumed `scripts/install.sh` installs them; it does not - that is `installer/linux/install.sh`, a different path. Rewriting a `.desktop` file the user may have customised, from an updater the criterion never really scoped, would be worse than leaving it.

**The rule that matters, and why:** `install.sh` has always overwritten bundled themes unconditionally, so editing one in place loses the edit on every install. The updater keeps a manifest of what it wrote and only overwrites a file that is byte-for-byte what it last put there. Everything else is kept and reported. The same rule makes the first run safe for every install that exists today: with no manifest, a file that differs is assumed to be the user's; a file that matches is adopted so the next release can update it normally.

**Other changes:**
- `crt update --finish-install <assets>` runs the same refresh headlessly, and `install.sh` calls it, falling back to its copy loops only for binaries too old to have the subcommand. One set of rules instead of two.
- `install.sh`'s `sudo xattr` is gone, replaced by a non-sudo `xattr -dr` with a comment on why it is only defensive. That line reliably did nothing except prompt for a password.
- `docs/how-to/update.md` and a README pointer.

**Verified end to end on macOS** with an optimised binary and a local release (`CRT_UPDATE_URL`, curl `file://`):

1. `crt update --finish-install assets` against a realistic config dir: 59 files written, 1 unchanged, the edited `dracula.css` kept and named in the output, `config.toml` untouched, manifest written. A second run writes nothing and still keeps the edit.
2. A full `crt update` over an install whose `dracula.css` had been edited: binary swapped, `crt.old` kept, the edit preserved (`MY OWN DRACULA`), a theme new in that release arrived.
3. Launching the updated binary: `crt.old` removed, `last_finished_version = "0.1.5"` recorded, `removed the previous version at ...` logged.

Tests cover the same ground at both levels: `refresh_assets` has a case per branch, and an `apply()` test installs a release carrying `assets/themes/` over a config dir with one edited and one untouched theme.
